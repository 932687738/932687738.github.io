运行时、业务模块和技术栈怎么分
模块边界 2026-10-26

仓库先分成能离线修改的治理仓，和必须启动的应用仓。应用仓再按 Maven 模块切开：一个运行时入口、若干业务上下文、一组可复用的 AI 库、以及共享的数据和缓存。

治理仓保存架构约束和接口契约，不跑对话。后端应用仓提供 REST 和 SSE。工作台、飞书长连接、外部命令行都是入口，进到应用服务之后走同一套用例。

功能按模块归位：

模块 对外能力 实现位置
application 唯一可执行进程，聚合依赖，导入各模块配置 启动类扫描 com.yxy.deepseek
agent-hub 智能体对话、意图路由、工具、会话历史与分享、可保存的流程 /api/agent-hub/*
knowledge-hub 知识库增删改、文档上传、检索问答 同在 /api/agent-hub 下：/chat/knowledge、/knowledge/upload、/knowledge-bases
aether-platform 智能体注册、技能版本、提示词模板、记忆、成本、追踪、平台对话 /api/super-agents/*
human-loop 图执行到危险工具时暂停，等人做出通过、拒绝或修改后再继续 恢复接口目前挂在图的演示入口上，能力本身是中断与恢复
bot-feishu 飞书消息接入与回发 长连接事件，不单独做一套编排
learning 聊天、图、推理循环的对照实验 /springai/demo/*，生产模块不依赖它

依赖向下。业务模块使用 AI 技术栈，不反向让技术栈依赖某个控制器。技术栈里：ai-core 放与框架无关的端口；ai-spring 放聊天客户端、嵌入和检索审计的公共配置；ai-alibaba 放图的构建基座；向量存储先有接口，再有 pgvector 实现；机器人有单独的契约，飞书去实现它。

跨模块的实现逻辑靠端口，不靠互相引用表。知识检索只有这一个出口，对话侧和平台侧各自写适配器去调用它：

平台上的检索工具不自己查表，而是把参数交给适配器，适配器再进这个端口：

return platformToolRetryExecutor.executeWithRetry(
        "searchPlatformKnowledge",
        () -> knowledgeRetrievalAdapter
                .search(query, knowledgeBaseId, tenantId)
                .orElse(ToolResult.fail("UNAVAILABLE", "Knowledge retrieval unavailable")));
```平台提供注册表和按任务选模型的能力，对话在编排时读取，不把平台的管理接口当成问答主路径。

配置由运行时的 `application.yml` 用 `spring.config.import` 拉入各模块的 YAML。本地密钥放在环境变量或被忽略的本地配置里。旧的单体目录还在清空，新功能写进上表对应模块。
