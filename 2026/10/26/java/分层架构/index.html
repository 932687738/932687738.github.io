服务端四层各自做什么
分层架构 2026-10-26

后端按接口、应用、领域、基础设施四层拆开。一层只做一种事：接口层收发，应用层编排用例，领域层守规则，基础设施层接数据库和外部系统。

这是 Spring Boot 应用里每个业务模块都要靠拢的目标形状。对话、知识库、平台治理三块都按这个切，避免控制器里写检索，或在图节点里写业务判断。

层 有哪些职责 实现时落在哪
接口层 校验入参、把 JSON 或文件转成用例入参、把流式结果推回客户端、统一错误码 web 里的 Controller 和 dto
应用层 按顺序调用预处理、路由、生成、后处理；划定事务；组装 SSE *ApplicationService
领域层 聚合、值对象、领域服务、仓储与检索的端口 domain，只依赖 JDK 和端口接口
基础设施层 MyBatis、向量库、模型与外部 HTTP 的适配、指标 infrastructure / repository

一次请求的实现逻辑是固定的。控制器不接触仓储，只调用应用服务。应用服务先跑预处理图，再按结果选流：

预处理图在启动时编译成单例，请求里只 invoke。节点写入状态，应用服务读快照，不把 HTTP 的请求对象传进图。图上的节点只在「状态」和「端口」之间搬运：读入状态，调用领域服务，把结果写回新的状态。选库、去重、分段、权限这类规则留在领域里。仓储接口定义在领域，MyBatis 实现放在基础设施，由 Spring 在启动时注入。

事务只包住本地落库。调用聊天模型、计算嵌入、访问外部工具协议，都放在事务提交之后或事务之外。这些调用慢，也会失败，不能和一次数据库提交绑在一起。

图在进程启动时编译成单例。请求进来只是执行，不为每一次问答重新编译。节点不引用接口层的请求对象，这样编排可以脱离某一种 HTTP 形状单独测试。

还在对齐的地方：部分检索和落库节点仍直接碰到仓储，业务判断有时写在节点里。目标是把规则收回领域服务，节点保持薄适配。
